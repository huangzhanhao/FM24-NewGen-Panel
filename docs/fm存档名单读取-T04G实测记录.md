## 4. 阶段二数据（渐进式分批渲染，liv 冷轮，实施提交 89bf461 / 6ece8ac）

对比（vs 阶段一 liv 中位）：M1 7074 → **154**（降 46 倍）；M2 1026 → **191**（降 5 倍，达标）；

M4 294 → **36**。M2 随块大小线性变化（32768 → 317ms 超阈），故 **`limit` 终值取 8192**。

## 5. §7.4 决策规则逐条比对（以阶段二 8192 档为准）

| 实测结果 | 判定 |
|---|---|
| M1–M5 全达标 | ✗（仅 M5 超） |
| 仅 M1 不达标、M2 达标 | ✗（M1 已达标） |
| M2/M3/M4 任一不达标 → 启用 §7.5 | ✗ **全部达标**（191/87/36），不启用 §7.5 |
| 仅 M5 不达标 → 先评估 `$state.raw`/浅代理 | **✓ 唯一超阈项**：+1093MB vs 400MB。评估结论：流式追加与 `$state.raw` 不兼容（raw 不追踪 push，需整体替换回 O(n²) 复制）；且 M5 包含 Rust 侧 `rtf_cache` 全量记录（架构要求，非前端可控）+ debug 构建放大（前端代理物化占大头），release 构建会显著低于该值。**不做 `$state.raw` 改造**，记入 R2 已知风险签字项 |
| M0 超 200 ms → spawn_blocking | ✗ M0 恒 0–63ms，**无需改造** |

## 6. 书面结论

1. **渐进式分批渲染生效**：M0–M4 五项全部达标（M1 154ms / M2 191ms / M3 87ms / M4 36ms），
   不启用 §7.5 后端分页（`pagedResource` 分页下推、`query_players_page` 第 4 条命令均不做）。
2. **`limit` 终值 8192**（`api.ts` 的 `PLAYERS_CHUNK_LIMIT`，提交 6ece8ac）：32768 档 M2 317ms 超阈。
3. **遗留 M5**（+1093MB > 400MB）：全量名单仍驻留前端内存（用户方案只解决「分批显示」，不解决
   「全量驻留」）；其中的可控部分（代理物化）与不可控部分（Rust 侧缓存、debug 放大）已评估，
   `$state.raw` 与流式追加不兼容，故不改造，作为 R2 已知风险登记。
4. 阶段一 32768/65536 两档未测的覆盖缺口，因用户裁决更换方案（渐进渲染）而失去意义：原三档
   对比只服务于「保留一次性全量时选块大小」的决策，该路线已被否决。
5. 真机验证的可重复方法见 §7；两阶段数据均由同一驱动、同一打点口径测得，可直接横向比较。
