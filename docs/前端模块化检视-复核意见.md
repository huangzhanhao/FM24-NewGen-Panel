## 二、需要修正的判断

### 2.1（最重要）「可在现有 12 个 vitest 用例保护下安全进行」——前提不成立

12 个用例的实际覆盖面：

- `app.store.test.ts` 8 个 → 全部是 `runTask` 的生命周期（点击清空 → 补 100% → 20s 后清空 → 新任务接管）
- `api.test.ts` 2 个 → 命令名与参数序列化
- `log.store.test.ts` 2 个 → 环形缓冲上限与级别过滤

而 P0 要改的正是**名单/快照标记协议**与 `replace:finished` 编排——这三处**零覆盖**。也就是说：P0 恰恰是「没有安全网」的那部分代码。这句结论如果不纠正，会直接诱导一次「改完跑一下绿的测试就提交」的裸奔重构。

正确顺序：**先补测试（把标记协议和事件编排写成用例）→ 再抽 action**。

### 2.2 「同一条业务编排出现在两处」——准确，但可抽的部分比说的小

精确核对写入的字段：

| 写入点 | 字段 |
|---|---|
| `SetupCard.scanRtf()` | `lastRtfScan`、`rosterReady=true`、`rosterVersion++`、`resultsView='table'` |
| `replace:finished` 回调 | `lastRtfScan`、`rosterReady=result==='finished'`、`rosterVersion++`、成功时 `snapshotReadPath` + `snapshotVersion++` |

重叠的是 3 个 + 2 个字段，但**「要不要切 Tab」是有意不同的**：扫描后跳「名单预览」让用户看到结果，替换结束后不动（用户可能正在看快照 Tab）。所以能抽的不是「合并成一个函数」，而是 `markRosterScanned(scan, { switchView })` 这类带语义开关的 action。这个区别在报告里被抹平了。

### 2.3 「两个表格重复约 40 行」——量级对，但可抽性被高估

两边各是「重置 effect + 300ms 防抖加载 effect」，确实同构。但差异比报告描述的大：

- PlayersTable 多：`sortKey / sortDesc / newganFilter` 三个筛选态、`oninput` 重置页码、拓展名单联动
- SnapshotPreview 多：`readable / xmlPath / imgDir` 依赖、blob URL 令牌与释放、卸载清理

一个 `createPagedResource` 工厂要容纳这些，就得开 `extraDeps` / `onReset` / `onLoaded` 三个钩子——**抽象出来的东西会比它消掉的重复更难读**。这在 Svelte 里还额外别扭：`$effect` 必须依赖组件初始化上下文（工厂函数在组件 setup 中调用才成立的隐式前提），把这条隐式约束变成新读者必须知道的知识。

我的判断：这条应从 **P1 降为 P3「可选」**，且只在出现第三个分页表格时再做。

### 2.4 「P0 拆分状态域」——机制上可行，但两处技术细节要补，收益也被高估

**(a) 技术上必须补的约束**

- **ES module 的 import 绑定不可重新赋值**。所以每个域只能导出「对象 + action」，不能导出裸 `let x = $state()` 再从别的模块赋值（Svelte 5 对此直接编译报错）。报告说的「各自导出 `$state`」在字面上会走不通，落地必然回到「对象 + action」形态。
- **域之间必然有依赖边**：`scheduleBarClear()` 的回调里判断 `appStore.taskRunning || appStore.snapshot?.replacing`（`app.svelte.ts:107`），`runTask` 也在写 `task`。拆完后 `progress.svelte.ts` 必须 import `profile.svelte.ts`。「四个互相独立的状态域」是不存在的，只是把同文件内的耦合换成了跨文件依赖。

**(b) 收益被高估**

拆分解决的是「改进度域会碰到名单域所在的那个文件」——即**同文件编辑冲突**。但代价是：

- 消费端 import 面变宽。`SetupCard` 拆后要 import：profile（snap / busy / browseMode）+ progress（runTask）+ roster（markRosterScanned）+ snapshotx（markSnapshotRead），由 1 个 `appStore` 变成 4 个模块。
- 报告的核心论据「任一关注点的改动都会触及所有组件共同依赖的文件」，**只解决了一半**：编辑冲突少了，但「这个状态到底在哪个文件」的检索成本上升了。

而更关键的：`displaySnapshot`、`browseMode` 这两个 getter 天然跨域（同时读 `snapshot` + `profilePreview` + `selectedProfile`），拆开后必须选一个域落脚并跨域读——这正好是上面 (a) 第二条说的新依赖边。

**单人项目里，这层收益是全部收益里最薄的。** 建议：等到第二个前端同事进场、或组件数超过 20 个再拆。

**(c) 如果确实要做，报告没给到位的更强版本**

报告说「组件和事件回调都调同一个 `markRosterScanned()`，协议就有了编译期入口」——**函数约定不是编译期入口，只是口头约定**，谁想直接写 `roster.ready = true` 依然写得下去。真正的编译期保护是：**该域不导出可变字段**，只导出 getter + action：

```ts
const state = $state({ ready: false, version: 0, scan: null as RtfScanResult | null });
export const roster = {
  get ready() { return state.ready },      // 只读
  get version() { return state.version },
  get scan() { return state.scan },
};
export function markRosterScanned(scan: RtfScanResult | null, opts: { switchView?: boolean }) { ... }
```

这样 `roster.ready = true` 编译期就过不去。这才是报告想表达的那个收益，值得写进方案。

### 2.5 `showError` vs `message(String(e))`——不是「两条路径」，是两套错误文案口径 + 一条错注

- `dialog.ts` 的 `showError`：`e instanceof Error ? e.message : String(e)`
- `PlayerViewer.svelte:43 / :75`：`message(String(e), ...)`

差异是实测可感的：后端返回 `Error` 时，前者显示 `xxx`，后者显示 `Error: xxx`。

而且 `PlayerViewer.svelte:42` 的注释写着「与『替换』失败同一反馈口径」——**实际替换失败走的是 `ReplacePanel` 的 `showError(e)`，两者口径不同**。这条注释会让下一个读者确信一个不成立的事实，属于应该立刻修的错注。

### 2.6 `onFinished(r: string)`——「既有联合类型」并不存在

`'' | 'finished' | 'cancelled' | 'failed'` 目前只是 `appStore.lastResult` 的**内联字段类型**，没有导出成命名类型。要用它，得先在 `types.ts` 里提成 `export type ReplaceOutcome = 'finished' | 'cancelled' | 'failed'`（顺带 `lastResult` 变成 `ReplaceOutcome | ''`），`app.svelte.ts:171` 那个 `as typeof appStore.lastResult` 的强转也随之消失。方向对，前提表述不准。

### 2.7 P2 「结构性样式移入 scoped」——这条会破坏现有布局契约，是报告里最该被否的方案

本项目至少有四处样式是**跨组件的布局契约**，必须留在全局：

1. **`.table-toolbar` / `.search` / `.pager`**（`app.css:723-732` + `TablePager.svelte:88-93`）：窗口变窄时靠 `.search`（`flex: 0 1 320px; min-width: 120px`）收缩，让 `flex-shrink: 0` 的分页器始终单行。这是**两个表格组件 + 一个分页器组件**三方共同遵守的约定。把 `.table-toolbar` 搬进任何一个组件的 scoped 样式，另一处就散架——而且这种散架是「窗口拉窄才出现」，回归测试很难发现。
2. **`table.grid`**：被 PlayersTable 与 SnapshotPreview 共用。
3. **`.btn / .card / .path-row / .seg3`**：多处复用（`.path-row` 被 SetupCard 与 ReplacePanel 共用）。
4. **设计令牌 + reset**：本来就是全局的，无争议。

更反讽的是：报告用「scoped 更安全」作为 P2 的论据，但现状里**恰恰是 scoped 造成了重复**——`.table-pane` 这段在 `PlayersTable.svelte:374-380` 与 `SnapshotPreview.svelte:175` 逐字重复了一遍。按报告的方向走，只会产生更多这种重复。

**正确的 P2 版本**：
1. 先立规则：「只有单组件独占、且不参与跨组件布局计算的样式才进 scoped」；
2. 把已经重复的 `.table-pane` **上收**到 `app.css` 与 `.table-toolbar` 并列（并注释说明它是后者的搭档）；
3. 其余按功能改动顺手迁移，不做一次性重写。

报告「不做一次性重写」这一句是对的，但方向要反过来。

## 三、报告漏掉的问题（按我判断的严重度排序）

### 3.1（高）「写后读」的时序正确性只存在于注释里

`app.svelte.ts:176-177` 注释：

> 这两个标记必须在 refreshSnapshot 之前置好：名单预览要立刻按新缓存重载一次。

这是一条**真实的业务正确性约束**——`rosterVersion++` 若晚于 `refreshSnapshot()`，名单预览会因为快照里的 `currentGroup` 已变而先重载一次、再被版本号触发第二次，出现一次多余的闪动/请求；顺序反了更会读到旧数据。而它**只写在注释里，没有任何机制保证**。

这比「两处赋值重复」危险得多：重复赋值是「改一处忘另一处」，时序错乱是「改一处顺序，另一个功能悄悄坏掉」。抽 action 时如果顺手把 `refreshSnapshot()` 也收进编排（或在 action 内部固定顺序），才真正消掉这个风险。**报告没看到这一层。**

### 3.2（高）拿「中文显示文案」当协议判据

- `PlayersTable.svelte:114-116`：`appStore.lastRtfScan?.format.includes("职员")` → 决定第 15 列表头是「所在地」还是「偏好工作」
- `PlayerViewer.svelte:83-85`：同一判据的复制

`format` 是后端给的**人可读文案**。一旦文案改词、加空格、做多语言，两个组件会**同时静默变形**，而且不会报错——只是列语义悄悄变错。

正确做法：后端在 `RtfScanResult` 里补一个结构化字段（如 `rosterKind: 'player' | 'staff'`），前端不再做字符串包含判断。这属于「协议值不许用文案表达」这条本已写在项目约定里的规则，被漏了。

### 3.3（中）`RtfScanResult` 之外还有两处重复定义

`types.ts` 里 `ProgressPayload` 与 `TaskProgressPayload` **字段逐字相同**（`status/value/current/total`）。项目记忆里明确写着「两条通道载荷形状必须一致」——既然如此，应该是一个类型 + 两个实例，或 `export type TaskProgressPayload = ProgressPayload`。现在的写法允许两条通道各自漂移，而它们的一致性恰恰是 `StatusBar` 能用一段渲染逻辑的前提。

### 3.4（中）单人替换的备份开关不联动

`PlayerViewer.svelte:20`：`const saveBackup = true;` 硬编码，注释写「与主界面备份开关联动可后续扩展」。实际行为：用户在「替换执行」面板关掉「保存备份」，仍会不点不知道地备份一次。这是**行为不一致**，不是风格问题。

### 3.5（低）`api.cancelReplace()` 缺少失败兜底

`ReplacePanel.svelte:133`：`onclick={() => api.cancelReplace()}`，无 `try/catch`。取消失败会变成未捕获的 Promise rejection（静默失败），而取消恰恰是用户焦虑时刻点的按钮。

### 3.6（低，但值得肯定的一点）

`appStore.lastResult` 报告归入「上帝对象」的负担里，暗示是冗余状态。实测它有读者（`Stepper.svelte:18` 判断第 5 步完成），不是死字段。拆分时它应落进 profile 域或事件编排域——**报告没有说明它该去哪**。

## 四、如果是我，会这样排

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0-a** | 补测试：名单/快照标记协议、`replace:finished` 编排（含**断言刷新顺序**） | 报告说的安全网不存在，必须先造 |
| **P0-b** | 抽 action：`markRosterScanned(scan, {switchView})` / `markSnapshotRead(path)`，并把 `refreshSnapshot()` 顺序收进编排；域内只导出 getter + action | 消掉 §3.1 的真风险，同时拿到报告想要的编译期保护 |
| **P1-a** | `format.includes("职员")` → 后端结构化字段 | §3.2，静默变形的正确性风险 |
| **P1-b** | `ReplaceOutcome` 命名类型 + `lastResult` 用上它 | 消掉两处强转 |
| **P2** | CSS：先立规则、把重复的 `.table-pane` 上收；`table-toolbar` 契约写进注释 | 方向与报告相反（见 §2.7） |
| **P3** | `$lib` 别名；PlayerViewer 改走 `showError`；`saveBackup` 联动；`cancelReplace` 兜底；两个进度载荷类型合一 | 零风险清理 |
| **不建议** | 拆 4 个 store 文件 | 单人项目收益最薄、跨域依赖新增、import 面变宽（见 §2.4） |
| **同意报告** | 不按 features/ 纵向切片 | 13 个组件的体量确实不必提前分层 |

## 五、保留意见

- 报告的**诊断**（横切集中、依赖注入、无循环依赖做得好；债务集中在 `appStore` 与隐式协议）我同意，方向没错。
- 报告的**证据强度**不够：拿不覆盖目标模块的 12 个用例当安全网、`746 行` 与 `40 行` 这类数字未标口径、`既有联合类型` 的表述经不起核对。给一份要指导重构的报告，这些应写成可核对的实测值。
- 报告的**最大问题不是说了什么，而是没说**：§3.1 的时序约束、§3.2 的文案当判据，都比它列出的 P0/P1 更值得先做。
