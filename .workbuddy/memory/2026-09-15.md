## 四个扫描类按钮接入底部状态栏进度（task:progress）

需求：点「检查完整性 / 扫描头像 / 扫描RTF / 读取快照」时，底部状态栏的进度条与百分比要实时反映进度，
数值口径 =「当前第 n 个 / 总待处理个」的百分比例。

后端（Rust，src-tauri/src/）：
- `commands.rs` 新增 `TaskProgressPayload { status, value, current, total }` + 事件名常量 `task:progress`
  + `TaskProgress` 上报器（`report(n,total)` / `finish()`；**只在百分比变化时 emit**——大名单逐行上报
  会刷爆 IPC，去重后最多 101 条事件）。四个命令加 `app: AppHandle` 参数，成功返回前调 `progress.finish()`。
- 进度单位（先拿到分母再逐项上报）：检查完整性 = 包内顶层条目（read_dir 是迭代器，先收集成 Vec 才有
  分母）；扫描头像 = 一级子目录；扫描RTF = 数据行（`table_rows(&text).count()` 先数一遍）；
  读取快照 = 映射条数（`RECORD_RE.find_iter().count()`）。后两者各多一趟纯内存轻量统计，不做字段解析。
- 扫描器新增 `*_progress(..., &mut dyn FnMut(usize, usize))` 变体：`scan_pack_progress`（拆成两趟：
  先列目录拿分母、再逐个一级子目录扫）、`scan_and_total_progress`、`check_integrity_progress`、
  `RtfScanner::parse_roster_progress`、`xml_parser::parse_xml_entries_progress`。

  `check_integrity` / `scan_and_total` 的无进度版改完就没有非测试调用方 → 直接删掉（否则 dead_code 警告），
  它们的测试调用点改调 `_progress` 并传空回调。**

## 复审上面这块功能（完整性 + 优化）

先复核上一条的实现：`check_integrity`/`scan_images`/`scan_rtf`/`read_snapshot` 四个命令的
`TaskProgress` 上报、四个 `*_progress` 变体的分母口径（顶层条目 / 一级子目录 / 数据行 / 映射条数，
`done` 都能走到 `total`）、StatusBar 与 SetupCard 的接线，均正确；`cargo test` 121 passed、
`svelte-check` 0 errors、`pnpm test` 9 passed。复审发现并修掉三处真实缺口：

1. **点击后残留上一个任务的名称与计数**（SetupCard 的四个扫描命令第一条 task:progress 要等后端读完
   文件、数出分母才发，扫描RTF/读取快照可达上百毫秒）。→ `runTask(fn)` 改成 `runTask(label, fn)`：
   进入时先把 `appStore.task` 清成 `{status: 任务名, value: 0}`；标签复用 `t.setup.*Btn`
   （与后端 `TaskProgress::new` 里的任务名同字）。
2. **几毫秒就结束的小包/空包完全看不到进度条**（`check_integrity` 14 目录、小包 `scan_images` 都是
   亚毫秒级，条子一闪即逝甚至不渲染），违背「点击即启用进度条」。→ `runTask` 在命令成功后补
   `value = 100, current = total`（后端 `finish()` 的同款口径；失败时不补，不谎报）。
   随之 StatusBar 的判据改为 `showTask = !replacing && (taskRunning || task.value > 0)`，
   「刚跑完」的 100% 会留在状态栏上，正好是需求里写的「● 就绪 ▬▬▬ 100%」。
   为避免取消替换后状态栏退回显示旧任务的 100%，`replace:progress` 监听里把 `task` 清零（替换优先）。
3. **两处漏接 runTask 的调用点**（同一条命令、状态栏只动进度条而状态文字还停在「就绪」）：
   SetupCard 的 `fixMissing` 复检、ReplacePanel 开始替换前的兜底校验。两处都改成经 runTask 调用
   （顺带把 `snap.currentGroup` 取到局部变量——闭包里 TS 判空收窄会失效）。

另外把 `check_integrity` 从同步命令改成 `async fn`：另外三个已是 async（注释写明「同步命令跑在主线程
会把界面卡住」），标准一平铺包顶层条目可达数万，留着同步会连 emit 带重绘一起堵住。这是一词改动，
`svelte-check` 与 `cargo test` 均无新增告警。

新增 `src-svelte/lib/stores/app.store.test.ts`（5 个用例）锁住 runTask 的契约：点击即切 0%、
小包补 100%、中途上报则 current 补齐到 total、抛错只复位 taskRunning 不补 100%。
验证：`pnpm test` 9 passed / 3 files；`pnpm check` 0 errors 0 warnings；`cargo test` 121 passed。

## 替换流水线也上报「第 n 个 / 共 total 个」+ 跑完 20 秒清空进度条

需求三件：①把 face_mapper、parse_xml 的操作也接到带 n/total 的进度口径（用户确认选「替换流程内部
也要 n/total」）；②解释「扫描头像分母粒度偏粗」；③跑完常驻 100% 改成 20 秒后自动清空。

后端（进度口径统一到「阶段区间 + 阶段内计数」）：
- `ProgressPayload` 加 `current`/`total`（纯阶段锚点传 0/0，前端据此不显示计数）——两条通道的
  载荷形状于是完全一致，StatusBar/ReplacePanel 的计数渲染只需一套。
- `replace_flow`：`progress` 回调签名改为 `&mut dyn FnMut(&str, u8, usize, usize)`，新增
  `ProgressFn` 别名 + 阶段区间常量 `STAGE_RTF(20,40) / STAGE_INDEX(40,46) / STAGE_XML(46,52) /
  STAGE_PLAYERS(52,80)` + `item()` 把 done/total 线性折算进区间。**区间必须相邻不重叠**，
  否则后一段的 0% 会把进度条拉回去（这是本次最容易踩的坑）。
  · parse_stage 改用 `parse_roster_progress`（20→40，逐数据行）；
  · map_stage 的扫盘改用 `FaceMapper::new(..., progress)`（40→46，逐一级子目录；命中 pre_scan
    缓存时无计数，锚点即 40）；逐球员抽图走 `generate_mapping` 的新 `progress` 形参（52→80）。
- `face_mapper`：新增 `MapStep { ReadXml, Players }` 枚举——两段进度必须落在不同区间，由调用方
  折算，本模块只报原始计数。`generate_mapping` 读现有 config.xml 改用新的
  `xml_parser::parse_xml_progress`；三个 `process_*` 的抽图循环逐球员报 `(i+1, total)`；
  **Preserve 的总数要用「过滤后要抽图的人数」**，拿 rtf_data.len() 当分母会永远走不满。
  每个子步骤开始先报一次 `(step, 0, 0)` 当锚点（Generate 没有 ReadXml 那步，Players 锚点是它
  唯一一次把状态栏从「读取头像包索引」切过来的机会）。
- `ProgressDedup`（commands.rs）：`replace` 通道的事件去重器，键 = **(阶段文案, 百分比)**。
  **键里绝不能带 current/total**——计数每项都在变，带上去等于没去重，照样刷爆 IPC。写了单测
  `progress_dedup_keys_on_status_and_value_only` 专门防这个回归。
- `commands.rs::check_integrity` 由同步改 async（平铺大包顶层条目可达数万，同步命令跑在主线程
  会把 emit 与重绘一起堵住）。
- 无进度版 `scan_pack` / `parse_roster` 在生产已无调用方（只剩测试用），改成 `#[cfg(test)]`
  而不是删掉——省去 ~39 处测试调用点的机械改动，效果与「删掉」一致（发布构建不再报 dead_code）。

前端：
- `types.ts` / `appStore.progress` 同步加 current/total；`StatusBar` 新增 `shown = showTask ? task
  : progress`，百分比与计数都从 shown 取（两条通道一套逻辑）；`ReplacePanel` 的进度文案也加上计数。
- 新增 `BAR_LINGER_MS = 20_000` + `scheduleBarClear()/cancelBarClear()`：runTask 收尾排一次清空，
  `replace:finished` 也排一次；新任务开始、`replace:progress` 推进时撤掉上一个定时器；定时器回调里
  再判一次 `taskRunning || replacing`（这 20 秒里用户可能又点了任务或开始了替换）。
  `app.store.test.ts` 加 3 个用例（用假定时器）：到点清空两条通道、20 秒内点新任务不清、
  20 秒内开始替换不清。

验证：`cargo test` 123 passed（无新增警告）；`pnpm test` 12 passed / 3 files；`pnpm check` 0 errors 0 warnings。
