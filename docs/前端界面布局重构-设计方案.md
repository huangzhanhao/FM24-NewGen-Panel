# 前端界面布局重构 · 设计方案

> 状态：仅设计，未实施
> 窗口基准：1280×800（`src-tauri/src/lib.rs` 的 `inner_size`）
> 结构：侧栏（作用域）+ 顶栏（一层导航，由 Stepper 改造）+ 三工作台 + 状态栏（只占内容列）

---

## 1. 结构总览

```
┌──────────────┬──────────────────────────────────────────────────┐
│              │  顶栏 · 由 Stepper 改造而来                       │
│  侧栏        │  ①存档资料 ● ─ ②头像替换 ● ─ ③AI生成头像 ③        │
│  = 作用域    │                                    右端：档 X · 组 Y│
│  存档 / 组   ├──────────────────────────────────────────────────┤
│  管理        │                                                    │
│              │  当前工作台（完整内容区，≈694px）                  │
│  ─────────── │                                                    │
│  主页 / 教程 │                                                    │
│  FAQ/Discord ├──────────────────────────────────────────────────┤
│              │  状态栏（≈1000 × 32，只占内容列）                  │
└──────────────┴──────────────────────────────────────────────────┘
```

### 1.1 侧栏 = 作用域，顶栏 = 动作

- **侧栏管「对谁做」**：哪个存档、哪个头像包组。所有工作台共用，因此不属于任何工作台，常驻左列（`Sidebar.svelte` 不动）。
- **顶栏管「做什么」**：三选一。
- 十字定位：**左列选作用域，顶栏选动作**。

### 1.2 状态栏不穿过侧栏（现状即如此，骨架图据此修正）

- `.statusbar { grid-column: 2 }`（`app.css:556`）、`.sidebar { grid-row: 1 / 3 }`（`app.css:184`）——状态栏本来就只占内容列。
- 侧栏底部 `.side-foot` 用 `margin-top: auto`（`app.css:240`）把四枚外链压到底部（`Sidebar.svelte:331-355`），正好占据左下角，状态栏无理由延伸过去。
- **由此定下一条约束**：状态栏宽度 = 内容区宽度（≈1000px），已排状态点 / 状态文字 / 进度条 + 计数 / 末条日志 / 日志按钮五项。**AI 队列进度不得进状态栏**——横向没有余量；纵向它是唯一一条全局带，也不该被第三条进度通道挤占（现有 `progress` / `task` 两条有单测锚着：`progress_dedup_keys_on_status_and_value_only`）。

### 1.3 工作台命名

| # | 名称 | 说明 |
| --- | --- | --- |
| ① | **存档资料** | 用「资料」不用「配置」：此台的产出不是应用设置，而是**让用户看清当前档手里有什么料**——头像包、RTF 名单、config.xml 快照、标准规则，外加名单 / 快照两个**验证视图**。描述性 |
| ② | **批量/单人头像替换** | 名字直接写清左栏的两件事：批量替换 + 单人微调。原名「批量替换头像」与内容不符——左栏有单人微调，「批量」二字是错的。动作性 |
| ③ | **AI 生成头像** | 动作性 |

### 1.4 顶栏 = Stepper 改造

不是另起炉灶，`Stepper.svelte` 的四个要素被继承：

| Stepper 现有 | 改造后 | 为什么保留 |
| --- | --- | --- |
| 序号圆 ①–⑤ | 序号圆 ①–③ | **让顺序显性**——顶栏不是平级标签页，是 1 → 2 → 3 的旅程 |
| 步骤间连接线 | chip 间连接线 | 保留「有序」语义，未走到的段不点亮 |
| `done` / `current` / 未到达 | chip 右侧状态点（灰 / 琥珀 / 绿） | 完成态语义直接继承 |
| 下方两行 hint（`Stepper.svelte:85-93`） | 移进工作台内的就绪卡 | 它是内容不是分界，条件出现 |

文案 `t.stepper.steps`（`text.ts:30`，现为 `['选档与头像包','校验与名单','选模式','执行替换','查看与微调']`）改为三工作台名。

**关键分离（否则改造会打架）**：

- **当前台 = 用户选择**（chip 高亮）——导航，必须可自由跳转。
- **该做哪一步 = 派生**（连接线点亮 + 状态点）——引导，沿用 `Stepper.svelte:8-26` 的派生口径。

两者各表达一件事：即使停在 ③AI 生成头像，若配置未就绪，①② 之间的连接线不会全亮、① 的状态点是琥珀。**「我在哪」和「我该做啥」分开说。**

### 1.5 顶栏右端：作用域回显

常驻显示「档 X · 组 Y」。理由：作用域在侧栏里，但用户目光在顶栏与工作台之间移动时，作用域是**判断一切的前提**——尤其 §5 定了「队列关联作用域」之后，切台时能否一眼看到当前档组，直接关系到会不会误判队列归属。

### 1.6 chip 状态点判据

统一三档，区分依据是**有没有可开工的最小前提**，不是「缺几项」：

| 色 | 含义 |
| --- | --- |
| 绿 | 该台开工条件全部满足 |
| 琥珀 | 最小前提已有，但缺 1–2 项（点进去看就绪卡补） |
| 灰 | 最小前提都不存在（基础条件未建立） |

| 工作台 | 绿 | 琥珀 | 灰 |
| --- | --- | --- | --- |
| ① 存档资料 | 已激活档 + 已选组 + 已设 RTF + 快照已读 | 有组，但 RTF / 快照缺其一 | 未激活档或无组 |
| ② 批量/单人头像替换 | `replaceReady` 三条件全满足（`app.svelte.ts:75-79`） | 三条件缺 1–2 | 无组 |
| ③ AI 生成头像 | 服务已连通 **且** 名单可读（`rosterReady`）且已选模型 | 缺其一 | 两者皆缺 |

- **绝不因状态点禁用 chip**——点进去才知道差哪一项，禁用等于把用户锁在外面。
- 台内**就绪卡**条件出现（非常驻）：一句话说明差哪几项 + 直达修复按钮，就绪后自动消失。内容来源沿用 `Stepper.svelte:40-48` 的 `missing` 派生。
- 现存的隐性收益：`replaceReady` 三个条件现在用户根本看不见差哪一项，只看到「开始替换」灰着。

## 2. 工作台一：存档资料

**由现有组件整体搬入，不重造**：`SetupCard.svelte:162-347` 原样保留（三条路径行、`use:pinScrollEnd` 长路径钉右、完整性状态行与一键修复、RuleEditor 入口）。

```
┌ 存档资料 · 当前档：XXX ─────────────────────────────────┐
│ 头像包路径  [只读输入]        检查完整性   扫描头像       │
│ RTF 名单    [只读输入]        选择 RTF     扫描 RTF       │
│ config.xml  [只读输入]        读取快照     查看位置       │
│ ● 完整性：完整（标准 2，共 28 目录）                     │
│ 标准规则                                                 │
└─────────────────────────────────────────────────────────┘
┌ 验证视图 ───────────────────────────────────────────────┐
│ [名单预览] [快照预览]        ← 全宽 ≈940px               │
│ 工具行：🔍 搜索  排序  状态筛选   ☑N 人 [加入队列(N)]    │
│ ……完整 18 列名单 / 快照树                                │
└─────────────────────────────────────────────────────────┘
```

- **不放单人微调**：此台是「看清手里有什么料」，单人微调是写操作，属替换台。
- **AI 服务卡不在此台**，归入 AI 台（§4.1）。此台保持纯粹的「存档侧资料」。
- **验证视图是新增价值**：「扫描 RTF」成功后不再跳去别处（`SetupCard.svelte:128` 的 `resultsView = 'table'` 改为切换本台内视图）；「读取快照」同理（`SetupCard.svelte:94`）。
- **验证视图是全宽 18 列名单**（≈940px），承担「审阅名单」职责——与替换台的窄栏精简名单分工，见 §3.3。
- **「加入队列」按钮放在名单视图的工具行，常驻可见**（见 §4.3）。理由：工具行本来就是「对当前筛选结果做点什么」的位置，与筛选/排序同处一行，用户勾完人抬手就点得到；若做成「勾选后浮出」，按钮会出现/消失导致工具行抖动，且未勾选时用户根本不知道有这个能力。

## 3. 工作台二：批量/单人头像替换

### 3.1 布局：读写分离左右分栏

```
┌ 替换执行 · 写 ────────┬ 结果视图 · 读 ─────────────────────┐
│ 模式 [保留][覆盖][生成]│ [名单预览] [快照预览]              │
│ 选中模式说明文字       │ 工具行：🔍 搜索  ☑N 人 [加入队列]  │
│ 选项 ☐重复 ☐过滤 ☑备份 │ 表头                              │
│ [▶ 开始替换] [取消]    │ 行 行 行 行 行 行 行 行 行 行       │
│                        │ 行 行 行 行 行 行 行 行 行 行       │
│ ───────────────────── │ 行 行 行 行 行 行 行 行 行 行       │
│ 单人微调 · 写          │ 行 行 行 行 行 行 行 行 行 行       │
│ UID [______] [查询]    │ 行 行 行 行 行 行 行 行 行 行       │
│ 头像 · 资料 · 当前映射  │                                    │
│ [选择图片] [替换该球员] │                                    │
└───────────────────────┴────────────────────────────────────┘
   左栏 320px                      右栏 670px
```

### 3.2 为什么是左右分栏而不是三个 Tab

**单人微调不该和「看结果」并列成第三个 Tab。** 它和批量替换同为**写操作**；名单 / 快照预览是**读操作**。按读写分栏，语义比 Tab 堆叠干净。

三条收益：

1. **纵向不再被第三个 Tab 抢高度**。结果视图从纵向方案的 ≈476px 变成**独占全高 ≈660px**。
2. **单人微调常驻可见**，不需要「从名单行下钻 → 再点返回」这条路径。
3. 它依赖的 `appStore.saveBackup`（`app.svelte.ts:36` 明确「批量替换与单人微调共用」）就在同栏上方，上下文连续。

### 3.3 代价与处理：右栏变窄了

现状结果区全宽 ≈1000px；分栏后右栏 670px，**18 列名单表必然横向滚动。**

处理办法（与存档资料台分工）：

| | 存档资料台 · 验证视图 | 替换台 · 结果视图 |
| --- | --- | --- |
| 宽度 | 全宽 ≈940px | 窄栏 670px |
| 列 | **完整 18 列** | **精简列集**（头像 / UID / 姓名 / 年龄 / 位置 / 当前映射），次要列可勾选展开 |
| 职责 | 审阅名单 | 看执行结果 |

理由：看执行结果主要关心「谁被换成了什么」，不需要全 18 列；完整审阅去存档资料台。

### 3.4 窄窗口退化：上下堆叠

窗口 <1100px（内容区 ≈852px）时 320 + 670 = 990 装不下，**退化为上下堆叠**：

- 上：**写**（替换执行 + 单人微调）全宽，高度自适应内容。
- 下：**读**（名单 / 快照结果视图）全宽，吃掉剩余高度。
- 顺序保持「写在上、读在下」——与左右分栏时的左写右读同序，也与「操作 → 看结果」的动作顺序一致。
- **断点用视口媒体查询**：工作台就是右列全部，窗口窄即内容区窄，与 `app.css:169-178` 既有 1180 / 1024 / 900 三档同口径，可直接沿用。

### 3.5 实施提示

- `ReplacePanel.svelte:187-193` 的 `.mode-line .seg3 { flex: 0 1 320px }` 是按全宽定的，进 320px 窄栏需改为纵向堆叠或缩小；同文件 `:202-218` 的 `@media (max-width: 900px)` 是**视口**断点，与 §3.4 的堆叠断点同类型，但与「左栏内部容器宽度」不是一回事，仍需分别处理。
- 单人微调沿用现有 `PlayerViewer` 组件，只换容器；其 `.tab-pane` 保活写法（`ResultsSection.svelte:31-33`）不再需要——常驻即可。

## 4. 工作台三：AI 生成头像

```
┌ 服务商 OpenAI ▾   模型 ▾   Key ●●●● 已设置  ●已连通  [测试连接] ┐  ← 服务配置条（全宽）
├──────────────────────┬──────────────────────────────────────────┤
│ 球员源 · 单人         │ 提示词 · 按该球员渲染后的正文             │
│ ┌──┐ 张三             │ 张三，24 岁，亚洲籍前锋，短黑发，肤色码 8…… │
│ │图│ UID 2000123456   │ 身高 181 · 俱乐部 X · CA 132 / PA 165     │
│ └──┘                  │ 字数 128 / 4500（该模型上限）             │
│ 年龄 24 · 位置 前锋   ├──────────────────────────────────────────┤
│ 种族 亚洲 · 肤色 8    │ 参数区 · 由服务商 + 模型的能力集回显       │
│ 发长 短 · 发色 黑     │ 尺寸 ▾  张数 ▾  质量 ▾  种子              │
│ 身高 181 · 俱乐部 X   │ 智能改写 ☐  水印 ☐  负向提示词            │
│ CA 132 · PA 165      ├──────────────────────────────────────────┤
│ [换球员] [加入队列]   │ [生成 1 张]  →  结果画廊                  │
├──────────────────────┴──────────────────────────────────────────┤
│ 队列坞 · 入队时 档 X · 组 Y · 3 / 12              [启动] [清空]  │
│ [图] 张三 · 24 · 前锋 · UID 2000123456 · 已完成                  │
│ [图] 李四 · 19 · 中场 · UID 2000456789 · 进行中                  │
└──────────────────────────────────────────────────────────────────┘
  左栏 ≈300px                右栏 ≈670px          队列坞 全宽 ≈150px
```

### 4.1 服务配置在台内

顶部一条全宽配置条：服务商 / 模型 / Key / 连接状态灯 / 测试连接。

- 它是一条横条而非一张卡，不侵占左栏纵向空间；顶栏塞不下 Key 输入，所以不上提。
- 未连通时顶部出现就绪卡：「未配置服务商 Key」+「去配置」直达本台配置条。

### 4.2 球员源 = 单人档案卡（不是多选列表）

左栏是一张**单个球员**的档案卡，不是名单列表。理由是提示词的变量就长在这张卡上：

`VARIABLE_HINTS` 有 15 个变量（`imageai.svelte.ts:11-16`：name / ethnicity / hairLength / hairColor / skinCode / gender / age / primaryNat / secNat / height / club / ca / pa / uid），卡片上直接列出其中**肉眼可核对的那几个**（年龄 / 位置 / 种族 / 肤色 / 发长 / 发色 / 身高 / 俱乐部 / CA / PA），用户扫一眼就知道变量会不会填错。

- 卡片三个来源：名单行「送生图」、单人微调「用此球员生成」、台内 UID 查询。
- 底部两个动作：**换球员**（重选单人）、**加入队列**（把当前这一人投进队列）。
- 名单未扫描时显示就绪卡：「请先扫描 RTF」+ 直达存档资料台。
- **不要快照一路**：球员源只走名单。

### 4.3 多人走「投递式入队」，不经过左栏

多人场景不进球员源卡，而是**在名单视图的工具行点「加入队列(N)」→ 条目落进队列坞**：

- 复用现有 `enqueuePlayers`（`imageai.svelte.ts:317-321`），它本就基于 `selectedInTable` 的 uid 集合 + `api.queryPlayers` 的当前页数据。
- 名单视图是共享组件（存档资料台全宽版、替换台 670 精简版），**两处都能投**：在存档资料台边审阅边勾一批，或在执行完替换后于替换台边看结果边勾下一批。
- 投递不需要跳转工作台——勾完继续勾，最后去 AI 台启动。这正是「队列常驻 + 顶栏角标」要支撑的用法。

### 4.4 参数区：沿用现状的能力驱动机制

**这一块相对现状是保持，不是改造。** `ImageAiPanel.svelte:596-646` 已经按 `modelInfo.capabilities` 显隐控件（张数按 `maxN`、质量按 `supportsQuality` + `qualities`、种子按 `supportsSeed`、尺寸走 `sizes` 预设），本次只是把这块整体挪进 AI 台右栏，机制不动。

完整的能力 → 控件映射（后端 `Capabilities`，`image_ai.rs:60-101` → 前端 `types.ts:126-139`）：

| 能力字段 | 参数区表现 |
| --- | --- |
| `sizes` | 尺寸下拉的枚举项；当前值不在枚举内自动落「自定义…」 |
| `sizeRules` | 自由尺寸的硬校验（minSide / maxSide / totalMin / totalMax / ratio），复用 `validateSizeRules`（`imageai.svelte.ts:26-51`） |
| `maxN` + `supportsN` | 张数上限；`supportsN=false`（z-image）时张数控件整体隐藏 |
| `supportsQuality` + `qualities` | 质量下拉显隐与取值域 |
| `supportsSeed` | 种子输入框显隐 |
| `supportsNegativePrompt` | 负向提示词输入框显隐 |
| `supportsPromptExtend` + `promptExtendDefault` | 智能改写开关显隐，切模型时归位到官方默认（`selectModel`，`imageai.svelte.ts:153-161`） |
| `supportsWatermark` | 水印开关显隐 |
| `maxPromptChars` | 提示词字数计数与上限校验 |

规则：

1. **选服务商 → 选模型 → 表单重排**。`selectProvider` / `selectModel` 已做参数归位（`:133-144`、`:153-161`），UI 只需按能力集显隐控件。
2. **新增能力 = 后端加字段，前端加一个控件分支**，不在前端写服务商 / 模型的 if-else。这就是架构文档已定的「能力声明单一通道」。
3. 尺寸不随切模型重置（现有口径，`:156-158`），沿用用户的自定义尺寸。

### 4.5 提示词预览：样本即球员源

球员源是单人，**样本就是当前这张卡**，预览永远按它渲染，不需要「勾了多人取第一个」这类规则。

- 复用 `api.previewPrompt(uid, templateId)`（`imageai.svelte.ts:201-202` 已在用）。
- 正文可编辑、可重新渲染；字数按 `maxPromptChars` 计数。
- 位置升为主区右栏顶部（≈670 × 90），不再挤在窄列里——15 个变量的填充结果要一眼扫得完。

### 4.6 队列坞常驻 + 顶栏角标

- 队列坞常驻本台底部，标题行标明**入队时的作用域**（呼应 §5）。
- **切走工作台怎么办**：在顶栏「③AI 生成头像」chip 上加**数量角标**。比引入状态栏第三条进度通道更轻——状态栏横向也没有余量（§1.2）。
- 队列条目的球员信息（头像 / 姓名 / UID / 年龄 / 位置）**从名单缓存取**，不存字段快照（见 §5.3）。

### 4.7 跨台入口

`sourcePlayer`（`imageai.svelte.ts:79`，`{uid, name}`）保留为「单人微调 → AI 台」的手递手参数，进入 AI 台后即成为球员源卡的内容：

- 不再是「跳 Tab」的手段（`PlayersTable.svelte:180-185` 那句 `resultsView = 'generate'` 可删）；
- 工作台内不再有独立的「数据源条」。

## 5. 队列与作用域

### 5.1 规则

| 情况 | 处理 |
| --- | --- |
| 队列空闲（无 running）时切档 / 切组 | **不作处理、不提示** |
| 队列运行中（有 running）时切档 / 切组 | **弹窗让用户确认**「将取消未完成任务」；确认 = 取消队列任务后切换，取消 = 留在原作用域 |

**为什么用弹窗而不是禁用侧栏**：禁用只告诉用户「不能点」，弹窗告诉他「为什么不能点 + 点了会怎样」，并且把决定权交回用户。`ask` 对话框已在这类场景用过（`Sidebar.svelte:87`、`:127`），无需新机制。

**队列空闲时不作处理，是承认一件事**：队列条目隐含绑定入队时的 (档, 组)——prompt 按该档球员信息渲染、产物要落进 `<组>/_generated/`。但空闲态下队列只是一堆**尚未执行的意图**，用户随时可自行清空或重选，此时强行清空或弹提示都是打断。真正有风险的只有「正在跑的时候换作用域」，那一条已经用弹窗挡住了。

### 5.2 后端不持久化

后端队列是**会话内存态**（与 Key 一样不落盘）：

- 重开应用队列为空，**不存在跨会话的作用域归属问题**，`QueueEntry` 无需加作用域标记字段。
- 与「队列空闲不处理」配合后，作用域问题收敛到「运行中的那一小段时间」，由弹窗兜住。

### 5.3 收益

- 队列存活期间名单缓存必然还在 → 队列坞能显示完整球员信息、提示词预览查得到样本。
- **`QueueEntry` / `PlayerRow` 结构不用改**（`PlayerRow` 仍只是 `{uid, name}`，`imageai.svelte.ts:265`）。
- 不靠冗余字段绕过一致性问题，也不需要新增清空逻辑。

### 5.4 一处护栏（显示，非弹窗）

既然空闲切换不清队列，队列条目可能在切档后仍带着旧档渲染好的 prompt。护栏是**显示而非打断**：

- 队列坞标题行常驻「入队时 档 X · 组 Y」；
- 顶栏右端常驻作用域回显（§1.5）。

两处对齐，用户一眼能看出「这批是在哪个档组入的队」。

**启动时是否再加一次硬校验（队列中含非当前作用域条目 → 确认后才启动）：暂不做。** 队列不持久化 + 空闲不处理，实际撞上的概率低；等实测真出问题再补，避免现在就为一个假设的风险加一道确认。
